ENIGMA COMPLETE-SEARCH LATENCY EXPERIMENT
Frozen protocol, executed 4 October 2026; results in MEASURED_RESULTS.txt

ONE PROPERTY
Elapsed wall-clock milliseconds for one complete 17,576-start-position search.
This matters because a local search interface must finish its bounded question
without missing candidates. All rotor/ring/reflector/plugboard settings and the
crib offset are known; only the three initial windows vary.

The comparator is the corrected full-message implementation, NOT the user's
unfinished historical prototype, wartime hardware, a Bombe or Alan Turing's work.
No comparison with historical computing is measured or implied.

BEFORE AND AFTER
baseline: enigma_lab.search.search_positions decrypts the entire ciphertext under
every starting position, then compares the known plaintext fragment (the crib).
early: enigma_lab.search_early.search_positions_early advances through the prefix,
then rejects a candidate at the first crib mismatch. A matching candidate needs
no further suffix transformation. Both continue through the entire domain and
return all matches in the same order with the same search metadata.

WHY THE CHANGE PRESERVES RESULTS
At the first crib comparison, both machines have consumed the same prefix and
are in the same state. Until a mismatch, they continue from identical state.
One mismatching character makes equality of the whole crib impossible. After all
crib characters match, the remaining suffix cannot change that match decision.
Every candidate starts from a fresh reset; none depends on a previous candidate.
Both validate the complete ciphertext, crib and domain before transformation,
including text that early rejection will never need to decrypt.

Early search uses public key_press(), which revalidates each character; baseline
uses process(), which validates each full message and loops internally. These
different call/validation costs are part of the end-to-end implementation being
compared. This experiment does not isolate the theoretical cost of pruning.

COMPLEXITY AND TRADEOFF
Let N be the number of candidates, L the message length, o the crib offset and c
the crib length. Baseline performs N*L letter transformations. Early search needs
between N*(o+1) and N*(o+c) transformations, including its prefix; a late crib
therefore limits potential work savings. Common validation costs O(L+c+N).
Both materialize the candidate domain and matches; neither algorithm becomes a
general search over unknown rotor order, ring settings or plugboard connections.
Reduced transformations are not a measured speedup. Python overhead may make
early search slower for short or late cribs; all outcomes must be reported.

FIXED INPUTS
Four workloads use three distinct saved ciphertexts, all with wide reflector B.
They are fixed examples, not a representative distribution of Enigma traffic:
- basic-B-5: published default five-letter example, full-length crib at offset 0.
  Complete expected match set is independently recorded as [AAA].
- ambiguous-B-1: one-letter seeded reference, full-length crib at offset 0.
  Short cribs can admit many starts; both must return all of them.
- early-B-97: seeded reference, 97 letters, first 12 plaintext letters as crib.
- late-B-97: the same 97-letter ciphertext, last 12 plaintext letters at offset 85.
The early/late pair holds key, ciphertext and message length constant while
changing the crib alignment; its actual crib text also differs.

Each ciphertext/known-key plaintext pair was generated by the pinned external
Py-Enigma reference corpus. For the seeded cases, the external fixture
supports known-key encryption, NOT an independently enumerated full match set.
Their complete expected sets are frozen by an untimed baseline/early preflight.
inputs.json retains exact inputs, settings, original starting windows and source
identifiers. INPUT_PROVENANCE.json records source hashes and evidence boundaries.

PROTOCOL FROZEN BEFORE PERFORMANCE MEASUREMENT
Five fresh processes per implementation and workload, forty workers total.
Each process makes one untimed warm-up call and two timed complete-search calls.
Its sample unit is the mean of those two calls. There are five process means per
implementation/case, not ten independent replicates. Every raw call is retained.

The plan contains a fixed schedule created with seed 1729. Case/replicate pairs
are shuffled; baseline and early workers remain adjacent within each pair.
First implementation is balanced 3/2 over five repetitions of each case and 10/10
over all twenty pairs. All workers run sequentially. Inputs never vary by seed.
Randomized order mitigates drift; it does not eliminate thermal or OS effects.
No best-of selection, outlier removal, adaptive calibration or early stopping.

The controller first checks full candidate equality, known-key inclusion,
completeness and exact counter invariants, saving an untimed reference. Workers
check warm-up and measured results against it. Incorrect output fails the run;
incomplete/failed runs are retained but do not receive a valid full summary.
Plan, input and implementation hashes are checked so edited experiments cannot
silently mix with the frozen comparison. These hashes establish provenance,
not an authenticity guarantee against deliberate edits to both files and locks.

TIMING BOUNDARY
perf_counter_ns() brackets the search API call only. It includes validation,
domain construction, Machine creation/reset, cipher work, counters and result
construction. It excludes process startup/imports, input/JSON I/O, reference
generation, warm-up, correctness comparisons, serialization and printing.
Garbage collection retains its normal enabled state. Record the actual timer
resolution, interpreter, OS, processor information and machine conditions.
Nanosecond timer units do not imply nanosecond measurement accuracy.

ANALYSIS
Per case/implementation: count, mean, median, sample standard deviation and sample
variance across five process means; ddof=1 (divide by n-1). Retain minima/maxima.
For each paired replicate report early-minus-baseline milliseconds and
baseline/early ratios, then summarize those five paired values. Ratio above 1
means baseline took longer in that pair. A mean of paired ratios is not a ratio
of grand means. Do not combine the four cases into a universal speedup.
These dispersions are across process means, not individual-request tail latency,
confidence intervals, or proof that a small observed difference is repeatable.

LIMITATIONS AND REPORTING
One user's machine, one interpreter run and four fixed workloads. No concurrency,
memory, cold start, full application/GUI latency or other reflector/variant claim.
Preserve every failed or interrupted run; report why a later rerun was needed.
The CLI still defaults to the unchanged baseline throughout the recorded experiment.
Do not switch defaults or alter workloads based on a desired result.
